# Agent Council：M1 雙 CLI PoC 計畫

狀態：草案 · 2026-11-10 · 對應規格 v0.6 第 12、13 節

## 1. 目的

本計畫定義 M1 的六個 PoC 與一項整合測試。PoC 的結果用來更新端點能力矩陣，並作為規格 v1.0 定稿（M2）的依據。

M1 要回答三個問題：

1. 流程控制器能否可靠地啟動兩家 CLI 的 headless session，並取得固定格式的結果？
2. 訊息能否送進既有的 session？送進去之後，session 是否真的開始工作？
3. 一家的 CLI 能否以唯讀權限審查另一家的 diff？

## 2. 範圍

| 在範圍內 | 不在範圍內 |
| --- | --- |
| PoC-04、PoC-05、PoC-06、PoC-13、PoC-14、PoC-15 | 桌面版與 SSH 的 PoC（PoC-01 至 PoC-03、PoC-07 至 PoC-11，在 M5） |
| 兩家 CLI 之間兩至三輪的問答往返 | A2A（PoC-12，在 P2） |
| 只在一台主機上執行 | 仲裁、簽核、ADR、Web 看板 |
| 用完即丟的測試程式 | 任何會併入正式版的程式碼 |

## 3. 規則

1. PoC 在維護者的本機執行。兩家 CLI 必須使用維護者以官方流程完成的訂閱登入（NFR-10）。
2. PoC 的程式碼放在 `poc/` 目錄。這些程式碼不可併入正式版；M3 開始前，必須刪除或移到封存分支。
3. PoC 使用專用的測試 repo。測試 repo 不可包含私有資料、金鑰或真實專案的程式碼。
4. PoC 不使用 API key，不使用 `claude --bare`（NFR-05、D-19）。
5. 每個指令在第一次使用前，必須先以 `--help` 確認實際的旗標。本計畫引用的旗標來自文件與第三方文章，可能與安裝的版本不同。
6. 報告與紀錄在提交前必須移除 token、帳號名稱、本機路徑與主機名稱。路徑以 `<repo>`、`<home>` 代替。
7. 任何會寫入測試 repo 以外位置的步驟，必須先由維護者同意。
8. 觸及用量上限時，立即停止，並把當時的輸出記入 PoC-05。

## 4. 環境紀錄

開始前記錄以下項目，並寫入報告：

- 作業系統與版本。
- Claude Code CLI 的版本（`claude --version`）。
- Codex CLI 的版本（`codex --version`）。
- 兩家 CLI 的登入方式（必須是訂閱登入）。
- 兩家各自使用的模型名稱。

## 5. PoC 項目

每個項目的報告必須包含：實際執行的指令（已移除敏感資料）、結束碼、輸出的格式、結論（通過、部分通過、不通過）、對規格的影響。

### PoC-04：headless 啟動與受控的設定

- **問題**：`claude -p` 與 `codex exec` 能否在保留訂閱登入的情況下，指定模型、限制為唯讀工具，並輸出固定格式的 JSON？
- **步驟**：
  1. 準備一份固定的輸入與一份輸出格式的定義。
  2. 兩家各執行三次。
  3. 記錄每次實際載入的設定檔、可用的工具與使用的模型。
  4. 確認 headless 模式是否載入記憶，以及能否關閉（規格 NFR-11）。記錄關閉的方法。
- **通過條件**：三次輸出都符合格式；工具確實是唯讀；模型與指定的相同；沒有使用 API key。記憶的結果只需記錄，不影響通過與否；不能關閉時，仲裁報告必須註明。
- **不通過時**：仲裁者改由人啟動（規格 PoC-04）。
- **預估回合**：6。

### PoC-05：用量上限的回報

- **問題**：CLI 觸及用量上限時，是否回傳可辨識的訊息或結束碼？
- **步驟**：
  1. 查閱兩家 CLI 的文件，記錄文件描述的行為。
  2. 不刻意耗盡用量。M1 期間如果自然觸及上限，記錄當時的完整輸出與結束碼。
- **通過條件**：有文件依據，或有一次實際紀錄，足以寫出辨識規則。
- **不通過時**：adapter 改以逾時判定，並通知人。
- **預估回合**：0。

### PoC-06：headless 不卡在核准提示

- **問題**：headless 執行遇到需要核准的工具呼叫時，會等待、失敗，還是略過？
- **步驟**：
  1. 兩家各以唯讀設定執行一個需要讀檔的工作。
  2. 兩家各以唯讀設定執行一個會嘗試寫檔的工作。
  3. 記錄行為、結束碼與耗時。
- **通過條件**：唯讀工作不需人介入即可完成；寫入的嘗試被拒絕，而且指令會結束，不會無限等待。
- **不通過時**：該端點不能自動多輪。
- **預估回合**：4。

### PoC-13：投遞到 Claude Code 的既有 session

- **問題**：一個已開啟的互動 session 能否收到外部訊息？能否被喚醒？
- **步驟**：對以下三種機制，分別在 session 為 idle、忙碌、已關閉時各測一次。
  1. hooks 把待辦注入收件匣。
  2. `asyncRewake` 喚醒 idle 的 session。
  3. 自訂 Channels（需要開發用旗標；選配）。
- **要記錄**：每種機制的啟用條件、訊息是否到達、session 是否開始新的回合、失敗時有沒有錯誤訊息。另外確認開發用旗標在 `claude -p` 下是否有效。
- **通過條件**：至少一種不需要開發用旗標的機制，能讓 idle 的 session 收到訊息。
- **不通過時**：既有 session 只用 `check_inbox`；自動回合由新的 headless session 執行。
- **預估回合**：9。

### PoC-14：`codex queue` 投遞到既有 session

- **問題**：`codex queue` 能否把訊息送到指定的 session？送達後 session 是否開始工作？
- **步驟**：
  1. 以 `codex queue --help` 確認旗標與指定 session 的方式。
  2. 在 session 為 idle、忙碌、未載入、背景服務不存在時各測一次。
  3. 每次記錄結束碼、輸出，並另外確認 session 是否真的開始工作。
- **通過條件**：idle 與忙碌兩種狀態下訊息都送達；有可靠的方法確認工作已開始（不可只看結束碼）。
- **不通過時**：既有 session 只用 `check_inbox`；自動回合由 `codex exec` 執行。
- **預估回合**：8。

### PoC-15：跨廠商的唯讀審查

- **問題**：一家的 CLI 能否以唯讀權限審查另一家產生的 diff，並回傳固定格式的結果？
- **步驟**：
  1. 在測試 repo 準備一份含有三個已知問題的 diff：一個邏輯錯誤、一個安全問題、一個超出需求範圍的變更。
  2. 以 `codex exec` 的唯讀沙箱審查，執行三次。
  3. 以 `claude -p` 的唯讀設定審查，執行三次。
  4. 每次記錄實際生效的權限、審查的 commit、輸出的格式、找到的問題。
  5. 每次審查後比對 repo 的狀態，確認沒有被修改。
- **輸出格式**：每項發現必須有穩定的 ID、嚴重度、位置、證據，以及與需求的關係。欄位與 engineering-workflow-core 的 findings 規定對齊。
- **通過條件**：三次輸出都符合格式；可以取得「實際生效的權限」的證據；repo 沒有被修改；超出需求範圍的變更至少兩次被指出。
- **不通過時**：該方向的跨廠商審查改由人啟動。
- **預估回合**：6。

## 6. 整合測試：兩家 CLI 的問答往返

- **目的**：證明一個問題可以在兩家之間自動往返，不需要人工轉貼。
- **做法**：
  1. 在 `poc/` 寫一個最小的 MCP server。它只提供兩個工具：讀取收件匣、提交訊息。它把訊息存進一個本機的 SQLite 檔。它只綁定 127.0.0.1。
  2. 兩家 CLI 各自註冊這個 MCP server。
  3. 在 `poc/` 寫一個最小的驅動程式。它依序啟動兩家的 headless session，每次只處理一個回合。
  4. 用一個真實但不敏感的技術問題，完成兩至三輪往返。
- **另外測試四種情況**：接收方 idle、接收方忙碌、接收方已關閉、MCP server 重啟後。
- **通過條件**：正常路徑完成兩至三輪，沒有人工轉貼；四種情況下訊息都沒有遺失；同一則訊息重送不會產生第二個回覆。
- **預估回合**：9。

## 7. 用量與時限

| 項目 | 預估 |
| --- | --- |
| 模型回合總數 | 約 40 至 50 個短回合（上列各項的總和，加上重試） |
| 時限 | 開始後兩週。逾時的項目記為「未完成」，並在報告中說明原因 |
| 執行順序 | PoC-04 → PoC-06 → PoC-15 → PoC-14 → PoC-13 → 整合測試。PoC-05 隨時記錄 |

回合數是依步驟估算的，不是量測值。先做 PoC-04 與 PoC-06，因為其他項目依賴它們的結果。

## 8. 交付

1. PoC 報告：`docs/reports/poc-m1-report.zh-TW.md`。每個項目一節，格式依第 5 節。
2. 更新後的端點能力矩陣（規格第 5 節）。
3. 規格修訂清單：每個 PoC 結果對應要修改的條文。
4. 給 engineering-workflow-core 的資訊：跨廠商 reviewer 路徑實際能提供哪些證據（來自 PoC-15）。

## 9. 驗收（M1 關卡）

1. 六個 PoC 都有結論，或有「未完成」的說明。
2. 整合測試通過第 6 節的條件。
3. 報告不含 token、帳號名稱、本機路徑或主機名稱。
4. 維護者簽核報告。

## 10. 風險

| 風險 | 處置 |
| --- | --- |
| CLI 的旗標與本計畫不同 | 規則 5：先以 `--help` 確認，並把差異記入報告 |
| PoC 佔用 claude-dev-skills 的開發用量 | 回合數很小；維護者可以隨時暫停。觸及上限時依規則 8 停止 |
| PoC 的程式碼被沿用到正式版 | 規則 2 |
| Channels 或 `codex queue` 的行為在 M1 之後改變 | 報告記錄已驗證的版本；NFR-01 的契約測試在 M3 之後接手 |
